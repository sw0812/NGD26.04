## 0. 개요 및 배포 컨텍스트

실제 Pixhawk 6X + Jetson Orin NX 하드웨어에서 동작하는 단일 창 Tkinter GUI. 사용자(파일럿/오퍼레이터)가 이 창 하나로:
1. 비행에 필요한 서브프로세스(ROS2 노드, 에이전트)를 켜고 끄고
2. 카메라 라이브 화면으로 비전 파이프라인 상태를 눈으로 확인하고
3. PX4 텔레메트리(자세/배터리/위치/ARM상태)를 실시간으로 보고
4. 비상시 즉시 개입(강제 착륙, 재부팅)할 수 있어야 한다.

전제: ROS2(Foxy) 환경이 소싱된 상태로 실행됨(`run_main.sh`가 담당, 범위 밖). Jetson에서 단일 X11 디스플레이(`:1`)로 실행.

# Part A — 기능 요구사항 (로직·데이터·동작)

화면에 어떻게 보이는지와 무관하게, **무엇을 계산/판단/실행해야 하는지**만 기술한다. 리팩토링 시 GUI 없이도(예: 유닛테스트로) 검증 가능해야 하는 부분들이다.

## A-1. 프로세스 생명주기 관리

### A-1.1 단일 인스턴스 락
- 동일 기기에서 이 GUI가 **동시에 2개 이상 실행되면 안 됨** — 각자 독립적으로 xrce 등을 같은 하드웨어 포트에 띄우면 충돌해서 텔레메트리가 아예 안 들어오는 장애가 실측됨.
- 락은 프로세스가 `kill -9`로 죽어도 OS가 자동 해제해야 함(파일 존재 여부 기반 PID 파일 방식은 "죽었는데 락은 안 풀림" 상태가 생겨서 부적합).
- 두 번째 실행 시도는 **정상 종료(exit code 0)** 해야 함 — 비정상 종료로 처리하면 바깥의 자동재시작 래퍼(`run_main.sh`)가 크래시로 오인해 무한 재시도하는 사고가 실측됨.

### A-1.2 시작 시 고아 프로세스 정리
- 시작 시, 이전 세션이 비정상 종료하며 남겼을 수 있는 서브시스템 프로세스(에이전트/카메라/아루코/착륙/미션 노드)를 패턴 매칭으로 찾아 먼저 정리해야 함 — 같은 장치/포트를 두 프로세스가 동시 점유하는 충돌 방지.

### A-1.3 서브시스템 프로세스 관리 (공통 규약)
관리 대상 6개: `xrce`, `camera`, `aruco`, `qgc`, `landing`(위험), `mission`(위험).

- 각 서브시스템은 **켜짐/꺼짐 두 상태**만 가지며, 현재 상태의 반대로 전환하는 단일 동작으로 제어되어야 함.
- 서브시스템 프로세스는 **프로세스 그룹 전체**를 종료해야 함 — 래퍼 프로세스(`ros2 run ...`)만 죽이면 실제 노드가 자식으로 살아남아 장치(`/dev/video0` 등)를 계속 점유하는 문제가 실측됨. SIGTERM 실패 시 SIGKILL로 승격.
- 컨테이너 기반 서브시스템(`qgc`)은 로컬 클라이언트 프로세스 종료와 별개로 **컨테이너 내부 프로세스를 정리하는 명령이 추가로 필요**할 수 있음.
- 실행 실패(실행파일 없음 등)는 조용히 무시하지 말고 기록되어야 함.
- 서브시스템의 stdout/stderr는 **끊기지 않고 끝까지 계속 소비**되어야 함 — 다 안 읽으면 OS 파이프 버퍼가 가득 차 자식 프로세스가 자기 출력에서 블록되어 멈추는 문제가 실측됨.

### A-1.4 서브시스템별 개별 로직
- **`xrce`**: 포트/baud는 실행 직전 사용자가 지정한 값으로 커맨드를 구성해야 함(하드코딩 금지 — 배선 방식에 따라 실제 장치 경로가 바뀜). GUI 프로세스 시작 시 기본값으로 **자동 시작**되어야 함(Jetson 쪽 에이전트 계층만 해결 — PX4 쪽 자동시작 여부는 별개 문제).
- **`camera`**: 표준 해상도/포맷(1280x720, MJPEG→RGB, 30fps)으로 실행, 카메라 보정 파일 경로를 참조해야 함. **웹캠 직접 테스트 모드(A-5.5)와 상호배타** — 동시에 같은 장치를 열 수 없으므로 한쪽 시작 시 다른 쪽을 먼저 정지시켜야 함.
- **`aruco`**: 파라미터 파일 기반 실행, 시뮬레이션 시간 미사용(실기체 전용 보장).
- **`qgc`**: Docker 컨테이너 경유 실행이 강제되어야 함(네이티브 실행은 호스트 제약으로 불가/위험).
- **`mission`**: 목표 마커 개수를 **실행 직전 사용자 입력값**으로 커맨드에 반영해야 함(고정값 불가), 숫자가 아니면 시작을 거부해야 함.
- **`landing`/`mission`**: 실제로 ARM/OFFBOARD 제어 명령을 PX4로 보내는 동작 — 시작 시 확인 절차가 없더라도(현재 정책, A-6.2 참고) **강제 착륙 기능이 항상 사용 가능해야 한다는 전제 조건**이 걸림.

## A-2. 로그 분류 로직
- 알려진 무해 패턴(예: TTS 미지원, GStreamer 관련 등 — 실제 비행 제어와 무관한 정상 로그)은 오류/경고로 **승격시키지 않아야 함**. 원문 로그 자체는 보존해도 됨, 승격만 안 시키면 됨.
- 알려진 장애 패턴은 심각도(오류/경고)와 해결 힌트를 함께 산출해야 함(예: GLIBC 버전, 카메라 인코딩 불일치, USB 연결 끊김, PX4 DDS 링크 끊김, Preflight 경고).
- 알려지지 않은 오류/경고도 최소 "확인 필요"로는 분류되어야 함(완전 누락 금지) — 단 과도하게 느슨한 키워드로 오탐을 내면 안 됨.

## A-3. 로그 영속화
- 세션마다 새 로그 파일을 만들어 모든 로그를 append해야 함 — 창을 닫으면 로그가 사라지는 문제 재발 방지. 디스크 쓰기 실패가 GUI 동작을 막아서는 안 됨(부가 기능 취급).

## A-4. PX4 텔레메트리 수신 및 파생 계산

### A-4.1 구독해야 하는 데이터
ROS2(uXRCE-DDS 경유)로 다음을 수신해야 함. **주의: 토픽 이름 버전 접미사(`_v1` 등)는 PX4 빌드/px4_msgs 조합마다 다르고, 안 맞으면 에러 없이 콜백이 평생 안 불리는 함정이 있음 — 배포 시마다 실측 확인 필요**:
- 자세(쿼터니언), 로컬 위치(x/y/z, 속도, 거리센서 유효성), 비행 상태(arming_state, nav_state), 배터리 상태, 페일세이프 플래그(local/global/home position invalid), ArUco 검출 결과(마커ID/거리/pose), 카메라 이미지 + 내부파라미터(K/D), 미션 상태 텍스트(기존 발행 토픽 재활용 허용), 카메라 정보.
- PX4로 명령을 보내는 발행 경로(VehicleCommand)도 이 계층이 제공해야 함(A-6 참고).

### A-4.2 파생 계산 로직
- **자세**: 쿼터니언 정규화 후 Roll/Pitch/Yaw(도 단위)로 변환.
- **상대고도**: 거리센서(`dist_bottom`)가 유효하면 그 값을 우선 사용(지형 추종에 더 정확), 무효하면 로컬 z(부호 반전)로 대체 — 이 우선순위를 반드시 지켜야 함.
- **속도**: 수평속도는 vx/vy의 벡터 합성, 수직속도는 부호를 반전해서 "상승=양수"가 되도록 함(NED 원본은 아래가 양수).
- **배터리 잔량**: PX4가 값을 못 구하면(`remaining < 0`) 퍼센트를 알 수 없음으로 처리해야 함(임의로 0%나 잘못된 값을 표시하면 안 됨).
- **위치추정 유효성 판정**: **local position invalid 여부만으로 판단**해야 함 — GPS 없는 비전 기반 세팅에서는 global(위경도)이 설계상 항상 무효이므로, global까지 같이 보면 local이 멀쩡해도 영원히 "불가"로 오판하는 버그가 실측됨. home position 없음은 별도 상태로 구분되어야 함.
- **연결/신선도 판정**: 모든 텔레메트리 값은 **마지막 수신 후 경과 시간**을 판단 기준으로 삼아야 함(값 자체가 있어도 오래됐으면 "무효/끊김"으로 취급) — 링크가 끊겼는데 마지막 값을 계속 유효한 것처럼 취급하면 안 됨.
- **서브시스템 연결 상태 판정**: 카메라/aruco처럼 "프로세스 실행 여부"와 "실제 동작 여부"가 다를 수 있는 항목은, **프로세스가 떠 있는지가 아니라 실제 데이터가 신선하게 들어오는지**로 판정해야 함.

## A-5. 카메라 비전 알고리즘

### A-5.1 ArUco 축 투영 계산
- 검출된 마커 pose(aruco 트래커가 이미 계산해서 보내준 값)를 바탕으로 XYZ 축의 화면 투영 좌표를 계산해야 함.
- **반드시 카메라 원본 해상도 기준 내부파라미터(K/D)로 투영 계산을 마친 뒤에 화면 크기로 축소**해야 함 — 축소 후 좌표를 계산하면 카메라 내부파라미터와 안 맞아 위치가 틀어짐. 이 순서는 아래 경계감지/라인트레이서 알고리즘의 축소된 이미지 처리와 **반드시 별개 단계**로 유지되어야 함.

### A-5.2 패드 경계 감지 알고리즘
- 색상 가정 없이 윤곽(엣지) 기반으로 사각형 형태를 찾아야 함.
- 오탐 방지 로직 필수: (a) 화면 경계에 닿은 윤곽 제외 (b) 종횡비 제한(너무 길쭉한 형태 제외) (c) 볼록성 필터(뭉개지거나 노치 있는 형태 제외).
- 최소 검출 크기(전체화면 대비 비율)는 가변 파라미터로 취급해야 함(고정값 금지).
- 프레임 단위 노이즈로 깜빡이지 않도록 **연속 검출/미검출 카운트 기반 히스테리시스**가 필요함.
- 검출 신뢰도 점수(0~100)를 산출해야 하며, 화면에서 크게(뚜렷하게) 잡힐수록 더 높은 점수를 줘야 함(흔들림 내성과 상관관계가 있다는 실측 근거).

### A-5.3 라인트레이서 알고리즘
- 실제 비행 미션(`search_phase_node.py`)이 쓰는 것과 **동일한 검출 로직**을 그대로 재사용해야 함(복제 금지 — GUI 표시와 실제 비행 동작이 어긋날 위험).
- 편차(e_y)/각도(e_psi)/교차점 여부를 산출해야 함.
- 품질 점수(0~100) 산출 규칙: 라인 폭이 두꺼울수록(신뢰 상한 이내) 가점, 각도가 과도하면 감점, 연속 검출 안정성에 보너스 — **"두꺼울수록 가점"** 방향성은 실측(두꺼운 라인이 블러/흔들림에 더 강함)에 기반한 것이므로 리팩토링 시에도 유지되어야 함.

### A-5.4 체스보드 캘리브레이션 계산
- 체스보드 코너를 원본 해상도에서 검출해야 함(정확도 보존, A-5.1과 동일 원칙).
- 캡처된 샘플들로부터 카메라 행렬/왜곡계수를 계산하고, 표준 형식(YAML)으로 저장해야 함.
- 최소 샘플 수(8장) 미만이면 계산을 거부해야 함.
- 계산 결과의 재투영 오차(RMS)를 산출해서 품질 판단 근거로 제공해야 함.

### A-5.5 웹캠 직접 캡처
- ROS2/usb_cam 파이프라인을 거치지 않고 장치에서 직접 프레임을 읽어오는 별도 경로가 있어야 함(카메라 자체 문제 vs ROS2 파이프라인 문제를 구분하는 진단 목적). `camera` 서브시스템과 동시에 같은 장치를 열 수 없음(A-1.4 참고).

## A-6. PX4 명령 발행 로직

### A-6.1 Pixhawk 재부팅
- 재부팅 명령 발행. **armed 상태에서는 PX4가 자체적으로 거부하도록 되어 있음 — 이 계층에서 armed 여부를 별도로 막을 필요는 없음**(PX4 내장 안전장치에 위임).

### A-6.2 강제 착륙 (AUTO.LAND 전환)
- 진행 중인 미션/랜딩 로직 상태와 **완전히 무관하게** PX4 내장 AUTO.LAND로 전환하는 명령을 발행해야 함 — 커스텀 OFFBOARD 정밀착륙 로직에 대한 의존이 전혀 없어야 함(마커를 놓치거나 미션 노드가 죽어있어도 착륙이 계속 진행되어야 함).
- 전송 유실 가능성에 대비해 **동일 명령을 짧은 간격으로 여러 번 반복 발행**해야 함.

### A-6.3 퍼블리셔 초기화 절차
- 순서가 있는 절차임: (1) xrce 에이전트 종료 → (2) ROS2 디스커버리 데몬 재시작 → (3) xrce 에이전트 재시작. 각 단계는 GUI 메인 스레드를 멈추지 않고 백그라운드에서 순차 진행해야 함.
- **알려진 한계(2026-09-28 확인, 문서화 필요)**: 이 절차는 "PX4 재부팅마다 세션이 누적되어 같은 토픽에 퍼블리셔가 여러 개 붙는 문제"에는 효과가 있으나, **같은 네트워크의 다른 기기가 동일한 `ROS_DOMAIN_ID`를 사용해서 생기는 텔레메트리 혼선에는 근본 해결책이 아님**(일시적으로 나아 보이다 재현됨). 이 기능의 책임 범위를 "도메인 격리와는 별개의 완화책"으로 명확히 구분해야 함.

## A-7. 종료 처리
- 종료 시: 모든 서브시스템 정지, 웹캠 직접 캡처 정지, ROS2 정상 종료, 로그 파일 닫기. 각 단계의 실패가 나머지 단계 수행을 막아서는 안 됨(최대한 정리 시도).

# Part B — UI/UX 요구사항 (화면·상호작용)

**무엇을 계산하는지가 아니라, 사람이 이 화면을 어떻게 보고 조작하는지**를 기술한다.

## B-1. 전체 레이아웃
- 단일 창, 세로로: (1) 상단 상태 요약 바 (2) 자세각 점검 바 (3) 본문(좌측 패널 + 카메라뷰/로그).
- 좌측 패널은 위에서부터: 서브시스템 토글 목록 → (비어있는 공간을 로그/오류 박스가 채움) → 비행 정보 박스 → 오류/경고 박스. **비행 정보 박스는 화면 크기가 바뀌어도 항상 하단에 고정**되어야 하고, 오류 박스가 그 위 남는 공간만 차지해야 함(비행 정보를 밀어내면 안 됨).
- 우측은 위에서부터: 카메라 모드 선택 행 → 모드별 튜닝 입력 행 → 카메라 뷰 박스 → 로그 박스.

## B-2. 서브시스템 토글 UI
- 각 서브시스템은 하나의 클릭 가능한 행(버튼)으로 표시되고, **켜짐/꺼짐이 시각적으로 뚜렷하게 구분**되어야 함(색/기호 변화).
- `mission` 항목 옆에는 목표 마커 개수 입력 필드가 함께 노출되어야 함.
- `xrce` 항목 옆에는 포트 선택(콤보박스, 후보값 제시) + baud 선택(콤보박스, 후보값 제시)이 함께 노출되어야 함.
- 위험 서브시스템(`landing`, `mission`)은 라벨에 **시각적 경고 표시**(예: "[주의]")가 있어야 함.
- **(2026-09-28 정책 변경)** `landing`/`mission` 시작 시 별도 확인 팝업은 없음 — 버튼을 누르면 바로 시작됨. 이 정책 변경은 반복 벤치테스트 편의를 위한 것이며, **이 정책이 유지되는 한 B-8(비상 명령 버튼)이 항상 화면에 노출되어 있어야 한다는 전제**가 딸려 있음.
- 실행 불가 사유가 있는 서브시스템은 눌렀을 때 그 사유를 사용자에게 보여줘야 함.

## B-3. 위험 동작 확인/경고 UI
- **Pixhawk 재부팅**, **강제 착륙**, **퍼블리셔 초기화**는 실행 전 확인 다이얼로그(예/아니오)를 거쳐야 함 — 각 동작이 무엇을 하는지(특히 강제 착륙은 "그 자리에서 바로 하강 시작") 다이얼로그 문구에 명시해야 함.

## B-4. 텔레메트리 표시 UI

### B-4.1 자세각 표시
- Roll/Pitch/Yaw를 실시간 텍스트로 표시 — 갱신 목적은 "손으로 기울였을 때 숫자가 바로 따라 바뀌는지"를 육안 확인하는 것(UART/브릿지 링크 진단).
- **고정폭 표시 필수**: 값의 자릿수/부호가 바뀌어도 옆 위젯이 좌우로 밀리면 안 됨.
- 데이터가 일정 시간 이상 오래되면 대시("─") 플레이스홀더로 되돌아가야 함 — 마지막 값을 계속 보여주면 링크 단절을 정상처럼 오판하게 됨.
- 자세를 **3D 와이어프레임으로도 동시에 시각화**해야 함 — 숫자보다 "실제로 기울인 방향과 같은 방향으로 도는지"를 직관적으로 확인 가능해야 함.

### B-4.2 배터리/비행정보 표시
- 배터리는 전압+잔량(%, 불명 시 "?%")과 **경고 레벨에 따른 색상 구분**이 함께 있어야 함.
- 상대고도/수평속도/수직속도/미션상태를 함께, 오래된 데이터는 자세각과 동일하게 대시로 되돌아가야 함.
- **ARM 상태 색상은 armed=빨강, disarmed=초록**이어야 함 — 이는 "위험 신호=빨강"이라는 의미이며, 다른 지표들의 "초록=데이터 정상수신"이라는 색 의미와 **정반대**임을 리팩토링 시에도 반드시 문서/주석으로 남겨서 혼동을 방지해야 함.
- 위치추정 유효성은 3단계로 구분 표시: 불가(빨강) / OK이지만 홈 없음(주황) / OK(초록).

### B-4.3 서브시스템 상태 요약(상단)
- 서브시스템 + PX4 연결 상태를 한눈에 보이는 요약(예: 상단 알약형 표시)으로 제공해야 함.
- **상태가 실제로 바뀔 때만 위젯을 재구성**해야 함 — 매 폴링마다 무조건 다시 그리면 X11 렌더링 요청이 누적되어 오래 켜두면 창이 죽는 문제가 실측됨. 이는 모든 주기 갱신 UI 요소에 공통 적용되어야 하는 원칙임.

## B-5. 로그/오류 패널
- 로그는 어느 서브시스템에서 온 줄인지 구분 가능한 형태로 한 곳에 표시.
- 오류/경고는 별도 패널에, 심각도별로 다른 색으로 구분 표시.
- 두 패널 모두 **무한정 쌓이면 안 되고** 일정 줄 수를 넘으면 오래된 것부터 잘라내야 함.
- **한 번의 갱신 틱에 반영하는 로그 줄 수를 제한**해야 함 — 한꺼번에 몰아서 그리면 렌더링 폭주로 창이 죽는 문제가 실측됨(여러 틱에 나눠 반영).

## B-6. 카메라 라이브뷰 UI

### B-6.1 모드 선택
- "일반" / "패드 경계 감지" / "라인트레이서(그리드)" / "캘리브레이션" 4개 중 **하나만 선택 가능**(라디오 버튼 형태).

### B-6.2 오버레이 배치 규칙 (일반/경계감지/라인트레이서 공통, 2026-09-28부터)
- ArUco 검출 시 XYZ 축이 화면에 그려져야 함(계산 자체는 A-5.1).
- "패드 경계 감지"/"라인트레이서" 모드에서는: **그 모드 고유의 검출 상태를 상단 배너**로, **ArUco 검출 상태는 별도의 하단 배너**로 — 두 정보가 서로 가리지 않게 분리 배치해야 함.
- "일반" 모드에서는 ArUco 상태가 곧 그 화면의 메인(상단) 상태.
- 모든 모드 공통: 화면 테두리 색으로도 현재 모드의 검출 성공/실패를 표시해야 함(성공=초록 계열, 실패/탐색중=빨강 계열).

### B-6.3 좌우 반전
- 사용자가 켜고 끌 수 있는 표시 전용 옵션. **오버레이(축/테두리/텍스트)까지 전부 합성된 최종 화면을 통째로 뒤집어야 함** — 검출 자체는 항상 원본 좌표계 기준으로 계산되므로, 뒤집힌 이미지 위에 나중에 오버레이를 그리면 위치가 어긋남.

## B-7. 카메라뷰 보조 컨트롤 UI

### B-7.1 경계 감지 튜닝
- 최소 검출 크기(%) 값을 사용자가 텍스트 입력으로 조절 가능해야 하며, 무엇을 위한 값인지 힌트 문구가 함께 있어야 함.

### B-7.2 캘리브레이션 컨트롤
- 체스보드 내부 코너 수(가로x세로), 칸 크기(mm) 입력 필드.
- "캡처"(현재 프레임을 샘플로 채택) / "계산+저장"(카메라 파라미터 계산·저장) / "초기화"(샘플 리셋) 3개 버튼.
- 현재까지 캡처된 샘플 수를 항상 보여줘야 함.
- 계산 완료 시 **재투영 오차와 저장 경로를 명확히 알리는 완료 알림**이 있어야 하고, "camera 서브시스템을 재시작해야 반영된다"는 안내도 포함해야 함.
- 웹캠 직접 테스트 버튼도 이 영역에 노출(버튼 텍스트/색으로 진행 상태 표시).

## B-8. 비상 명령 버튼
- **"강제 착륙"** 버튼은 다른 버튼과 뚜렷이 구분되는 강조 색(경고색 계열)으로, 항상 눈에 띄는 위치(자세각 점검 바)에 있어야 함 — 비상 상황에서 바로 찾을 수 있어야 하므로.
- "Pixhawk 재시작", "퍼블리셔 초기화" 버튼도 같은 바에 위치.

## B-9. 렌더링 성능/폴링 제약
- 주기 갱신 루프 3종(로그, 텔레메트리, 카메라)은 각각 독립적으로 재스케줄되어야 하며, **어떤 이유로든(데이터 미도착 등) 중간에 재스케줄이 멈추면 그 갱신 루프는 영구히 죽는다** — 재스케줄 호출은 반드시 그 함수의 모든 실행 경로에서 도달 가능한 위치에 있어야 함. (실측 사고: 자세 데이터가 아직 없을 때 3D 렌더 함수 자체가 호출되지 않아, 그 함수 끝에 있던 재스케줄 줄까지 같이 실행이 안 되어 갱신 루프가 영구 정지한 사례가 있었음 — 반드시 회귀 방지.)
- 폴링 주기는 실측 튜닝값(로그 150ms, 텔레메트리 100ms, 카메라 50ms)이며, 너무 빠르면 렌더링 폭주, 너무 느리면 반응성 저하 — 변경 시 재검증 필요.
- 위젯 재구성은 "상태가 실제로 바뀐 경우"로만 제한해야 함(B-4.3 참고, 전 UI 요소 공통 원칙).

# Part C — 비기능 요구사항 / 제약사항

Part A/B 어디에도 딱 들어맞지 않지만 리팩토링 시 반드시 유지해야 하는 시스템 차원의 제약들.

- **QoS**: PX4 `/fmu/out/*`, `/fmu/in/*` 토픽 구독/발행은 `BEST_EFFORT`+`VOLATILE`+`KEEP_LAST`(depth 5)로 맞춰야 uXRCE-DDS 브릿지가 정상 동작함(`TRANSIENT_LOCAL`로 하면 브릿지가 아예 안 이어주는 문제가 실측됨).
- **토픽 이름 버전 접미사 하드코딩 금지**: 배포 환경마다 실측 확인 절차 필요(px4_msgs/펌웨어 조합이 바뀌면 이름이 바뀌고, 안 맞아도 조용히 깨짐).
- **환경변수 기본값**: `ROS_DOMAIN_ID`(기본 0 — **2026-09-28 확인: 같은 네트워크에 이 기본값을 쓰는 다른 기기가 있으면 텔레메트리가 섞이는 심각한 문제 있음. 리팩토링 시 기본값을 프로젝트 고유값으로 바꾸는 것을 고려할 것**), `DISPLAY`(기본 `:1`).
- **절대경로 하드코딩**: 현재 `/home/sasllab/...` 형태 경로가 다수 박혀있음(카메라 보정 파일, 미션 노드 경로, aruco 파라미터 파일 등). Raspberry Pi 배포판에서는 `$HOME` 기반으로 재작성한 이력이 있음 — 리팩토링 시 설정 파일/환경변수로 애초에 분리 권장.
- **전역 가변 딕셔너리(`SUBSYSTEMS`) 런타임 변경 패턴**: `mission`(마커 개수), `xrce`(포트/baud)는 시작 직전 전역 설정을 직접 덮어써서 반영하는 방식 — 모듈화 시 더 명시적인 설정 객체 전달 방식으로 바꾸는 게 좋음.

# Part D — 알려진 구조적 문제 및 모듈 분리 제안

- **God-object**: `App` 클래스 하나가 Part B(UI) 전체와 Part A(기능) 상당수(카메라 비전 알고리즘, PX4 명령 발행 트리거)를 동시에 담당. `TelemetryNode` 클래스 하나가 Part A-4(ROS2 구독/파생계산) 전체를 담당.
- 제안 모듈 분리(강제 아님, Part A/B 구분과 대응됨):
  - `subsystem_manager` — A-1 (프로세스 생명주기)
  - `log_classifier` — A-2, A-3 (분류 로직 + 영속화, 순수 함수로 분리하기 쉬움)
  - `telemetry_node` — A-4 (ROS2 구독 + 파생 계산, GUI 의존성 없이 테스트 가능해야 함)
  - `camera_vision` — A-5 (ArUco 투영/경계검출/라인트레이서/캘리브레이션 계산 — **입력은 numpy 배열, 출력은 결과값+오버레이된 배열**이 되도록 설계하면 GUI 없이 단위테스트 가능)
  - `px4_actions` — A-6 (명령 발행 로직)
  - `gui` (Part B 전체) — 위 모듈들의 결과를 화면에 배치하고 사용자 입력을 각 모듈로 전달하는 역할만, 계산 로직은 갖지 않아야 함.
